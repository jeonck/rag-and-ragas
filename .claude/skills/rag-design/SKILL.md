# RAG 설계

RAG 프로젝트가 실패하는 방식은 거의 정해져 있다. 파이프라인은 첫 주에 돌아가고, 데모는 잘 되고, 그다음 6개월 동안 "가끔 이상한 답을 한다"는 말을 들으면서 아무도 그게 나아졌는지 나빠졌는지 말하지 못한다. 측정 없이 튜닝했기 때문이다.

이 스킬은 그 순서를 뒤집는다. **측정 가능한 상태를 먼저 만들고, 그다음 설계한다.**

## 핵심 원칙

1. **골든셋이 코드보다 먼저다.** 실제 질문 30~50개와 정답 근거 문서를 확보하기 전에는 청크 크기나 벡터 DB를 고르지 않는다. 골든셋이 없으면 이후 모든 결정이 취향 논쟁이 된다.
2. **RAG 실패의 대부분은 검색 실패다.** 생성 모델을 바꾸기 전에 "정답이 들어 있는 문서가 컨텍스트에 들어왔는가"를 먼저 본다. 이 둘을 분리해서 측정하지 않으면 엉뚱한 곳을 고치게 된다.
3. **베이스라인부터 간다.** 고정 크기 청킹 + 하이브리드 검색 + 리랭커 + 인용 강제. 이게 첫 버전이다. GraphRAG, agentic RAG, 파인튜닝은 베이스라인이 측정된 한계에 부딪힌 뒤에 꺼낸다. 처음부터 복잡한 구조로 시작하면 무엇이 기여했는지 영원히 모른다.
4. **모든 결정에 재검토 조건을 붙인다.** "청크 512 토큰"이 아니라 "청크 512 토큰 — 근거: 문단 평균 길이 / 측정: context_recall / 재검토: recall 0.8 미만이면 1024로". 근거 없이 굳은 숫자가 나중에 아무도 못 건드리는 상수가 된다.

## 설계 절차

### Step 0 — 요구사항 인터뷰

바로 아키텍처를 그리지 말고 먼저 묻는다. 아래 7개는 각각 **설계를 실제로 바꾸는** 질문이다. 사용자가 이미 답한 것은 건너뛰고, 모르면 "모름"으로 두고 진행하되 설계 문서에 가정으로 명시한다.

1. **질문 유형** — 단일 사실 조회 / 절차 안내 / 요약·종합 / 비교·분석 중 무엇이 주력인가. (→ 청크 크기, top-k, 쿼리 분해 여부)
2. **코퍼스** — 문서 수, 총 용량, 형식(PDF·HTML·표·코드·스캔본), 언어, 갱신 주기. (→ 파싱 난이도, 인덱싱 전략, 임베딩 모델)
3. **정답의 소재** — 정답이 보통 한 문단에 있나, 여러 문서를 합쳐야 하나. (→ multi-hop 필요 여부, 이게 있으면 베이스라인으로 안 된다)
4. **접근 제어** — 사용자마다 볼 수 있는 문서가 다른가. (→ 메타데이터 필터는 나중에 못 붙인다. 있으면 인덱스 설계에 처음부터 넣는다)
5. **오답의 비용** — 틀린 답이 나갔을 때 무슨 일이 생기나. 사내 위키 오답과 의료·법률·금융 오답은 다른 시스템이다. (→ 인용 강제, 모른다고 답하는 정책, 사람 검토 단계)
6. **예산** — p95 지연 목표, 월 예상 쿼리 수, 비용 상한. (→ 리랭커 유무, 모델 선택, 캐싱)
7. **현재 상태** — 신규인가, 개선인가. 개선이면 **지금 실패하는 실제 사례 10개**를 받는다. 이게 골든셋의 씨앗이자 가장 값진 입력이다.

`references/discovery.md`에 답변→설계 매핑표와 설계 카드 템플릿이 있다.

### Step 1 — 골든셋 만들기

설계 전에 평가 대상을 고정한다. 최소 30문항, 가능하면 50문항.

각 항목: `질문` / `정답(ground truth)` / `정답 근거 문서 ID·구절`. 구성 비율은 대략 실제 질문 분포를 따르되, 다음을 의도적으로 섞는다.

- 코퍼스에 답이 **없는** 질문 (10~20%) — 모른다고 답하는지 보는 용도. 이게 없는 골든셋은 할루시네이션을 측정하지 못한다.
- 여러 문서를 합쳐야 하는 질문
- 표·각주·부록처럼 파싱이 깨지기 쉬운 곳에 답이 있는 질문
- 동의어·약어·오타가 섞인 실제 사용자 말투

만드는 방법과 LLM 합성 시 주의점은 `references/evaluation.md`.

### Step 2 — 베이스라인 확정

여기서 판단할 것은 "최선"이 아니라 "출발점"이다. 기본값은 이렇게 잡고, Step 0 답변이 벗어날 이유를 줄 때만 바꾼다.

| 단계 | 베이스라인 기본값 | 벗어날 신호 |
|---|---|---|
| 파싱 | 텍스트 추출 + 표는 마크다운으로 | 스캔 PDF·복잡한 레이아웃 → 레이아웃 인식 파서 |
| 청킹 | 512 토큰, 15% 오버랩, 문단 경계 우선 | 짧은 FAQ → 문서 1개=1청크 / 긴 절차서 → parent-child |
| 메타데이터 | 출처, 제목, 섹션, 날짜, 권한 태그 | 접근 제어 있으면 필수 |
| 임베딩 | 다국어 모델 (한국어 포함 시 bge-m3 / multilingual-e5-large) | 도메인 전문 용어 다수 → 도메인 모델 검토 |
| 검색 | 하이브리드(BM25 + 벡터), top-k 20 | 고유명사·코드·에러코드 많을수록 BM25 비중↑ |
| 리랭킹 | cross-encoder 리랭커로 20 → 5 | 지연 예산이 극도로 빡빡하면 생략하고 top-k 축소 |
| 생성 | `claude-opus-5`, 인용 필수, 근거 없으면 모른다고 답변 | 대량·저비용 경로는 `claude-sonnet-5` |
| 평가 | RAGAS 4지표 + 회귀 게이트 | — |

단계별 상세는 `references/ingestion.md`, `references/retrieval.md`, `references/generation.md`.
베이스라인을 넘어서는 구조(parent-child, multi-query, agentic, GraphRAG)는 `references/patterns.md` — **언제 필요해지는지의 신호와 함께** 정리돼 있다.

### Step 3 — 평가 계획

설계 문서에 파이프라인만 쓰고 평가를 "나중에"로 미루면 이 스킬을 쓴 의미가 없다. 지표와 임계치를 설계 시점에 박는다.

| 지표 | 무엇을 보는가 | 초기 목표 |
|---|---|---|
| `context_recall` | 정답 근거가 검색 결과에 들어왔나 | ≥ 0.85 |
| `context_precision` | 들어온 것 중 쓸모 있는 게 위에 있나 | ≥ 0.70 |
| `faithfulness` | 답이 컨텍스트에만 근거하나 (할루시네이션) | ≥ 0.90 |
| `answer_relevancy` | 답이 질문에 실제로 답하나 | ≥ 0.85 |

숫자 자체보다 중요한 건 **이 4개를 함께 본다는 것**이다. faithfulness만 높으면 "모르겠습니다"만 반복하는 시스템도 만점이 나온다.

실행 하니스는 `scripts/ragas_eval.py` — 골든셋 JSONL과 파이프라인 함수를 받아 지표를 내고, 임계치 미달이면 exit code 1을 던져 CI 게이트로 쓸 수 있다. 지표 해석과 RAGAS 버전 주의사항은 `references/evaluation.md`.

### Step 4 — 설계 문서 작성

`assets/design-doc-template.md`를 채운다. 결정마다 **근거 / 측정 지표 / 재검토 조건** 세 줄이 붙어야 한다. 이 템플릿이 이 스킬의 최종 산출물이다.

### Step 5 — 개선 루프

한 번에 하나씩 바꾸고 골든셋으로 재측정한다. 두 개를 같이 바꾸면 기여도를 못 가른다. 증상별 진단은 아래 표.

## 진단표 — 증상에서 원인으로

| 증상 | RAGAS 신호 | 1순위 원인 | 먼저 해볼 것 |
|---|---|---|---|
| 문서에 없는 내용을 지어냄 | faithfulness↓, context_recall 정상 | 생성 | 인용 강제, "근거 없으면 모른다고 답하라" 명시, 컨텍스트 밖 지식 사용 금지 |
| 관련 문서를 아예 못 찾음 | context_recall↓ | 검색 | 하이브리드 검색, 쿼리 재작성, 청크 크기, 임베딩 모델 교체 |
| 관련 문서는 있는데 답이 부실 | context_precision↓, recall 정상 | 랭킹 | 리랭커 도입, top-k 축소, 중복 청크 제거 |
| 질문과 겉도는 답 | answer_relevancy↓, 나머지 정상 | 프롬프트 | 프롬프트 구조, 질문 의도 분류, 출력 형식 지시 |
| 여러 문서 종합 질문만 실패 | multi-hop 문항에서만 recall↓ | 쿼리 전략 | 쿼리 분해(decomposition), 단계적 검색 |
| 답은 맞는데 느림 | — | 파이프라인 | 리랭커 배치화, 프롬프트 캐싱, top-k 축소 |
| 특정 문서군에서만 실패 | 문항 그룹별 recall↓ | 파싱 | 해당 원본의 파싱 결과를 눈으로 확인 — 표·각주가 깨졌을 확률이 높다 |

마지막 행이 실무에서 가장 자주 걸린다. 지표가 이상하면 벡터 DB를 의심하기 전에 **청크 20개를 직접 읽어본다.**

## 참조 파일

필요할 때만 읽는다. 전부 읽을 필요 없다.

- `references/discovery.md` — 인터뷰 심화, 답변→설계 매핑표, 설계 카드 템플릿
- `references/ingestion.md` — 파싱, 청킹 전략 비교, 메타데이터 스키마, 인덱싱
- `references/retrieval.md` — 임베딩 모델 선택, 벡터 스토어, 하이브리드/BM25, 쿼리 변환, 리랭킹, 권한 필터
- `references/generation.md` — 컨텍스트 배치, 프롬프트 템플릿, Claude 인용 API, 프롬프트 캐싱, 모델·비용표, abstain 정책
- `references/evaluation.md` — 골든셋 제작, RAGAS 지표 정의·해석, 임계치, 회귀 방지
- `references/patterns.md` — 아키텍처 패턴 카탈로그와 각각이 필요해지는 신호
- `references/operations.md` — 인덱스 갱신, 모니터링, 캐싱, 보안, 롤아웃
- `assets/design-doc-template.md` — 설계 문서 템플릿 (최종 산출물)
- `assets/golden-set-sample.jsonl` — 골든셋 예시 6문항 (형식과 구성 비율 참고용)
- `scripts/ragas_eval.py` — RAGAS 평가 하니스

## 안티패턴

- **골든셋 없이 튜닝** — 가장 비싼 실수. 체감으로 좋아졌다는 말은 데이터가 아니다.
- **컨텍스트가 크니까 검색을 대충** — 1M 컨텍스트가 있어도 노이즈는 정확도를 떨어뜨리고 비용을 올린다. 검색은 비용 절감 장치가 아니라 정확도 장치다.
- **청크 크기부터 논쟁** — 청크 크기는 recall을 측정하면 30분이면 정해진다. 회의로 정하지 않는다.
- **실패 사례를 안 읽음** — 실패한 쿼리 10개의 검색 결과를 직접 읽는 것이 지표 대시보드 한 달치보다 정보량이 많다.
- **인용 없이 출시** — 사용자가 답을 검증할 방법이 없으면 신뢰는 첫 오답에서 끝난다.
- **한 번에 여러 개 변경** — 기여도 분해 불가. 반드시 하나씩.
