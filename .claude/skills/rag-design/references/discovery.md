# 요구사항 인터뷰 심화

SKILL.md Step 0의 7개 질문을 실제로 어떻게 끌어내고, 답이 설계의 무엇을 바꾸는지.

## 인터뷰 진행 방식

사용자는 보통 "우리 문서로 챗봇 만들고 싶다"까지만 말한다. 여기서 7개를 한꺼번에 던지면 취조가 된다. 대신 이렇게 한다.

1. **먼저 코퍼스 실물을 본다.** 접근 가능하면 문서 5~10개를 직접 연다. 이 10분이 질문 20개보다 많은 걸 알려준다 — 표가 많은지, 스캔본인지, 문서마다 양식이 다른지, 목차가 있는지.
2. **사용자에게 실제 질문 10개를 요청한다.** "어떤 질문에 답해야 하나요"가 아니라 "실제로 사람들이 물어본 것 10개를 그대로 주세요". 가공된 예시 질문은 실제 분포를 왜곡한다.
3. **나머지는 그 10개를 보면서 확인한다.** 대부분의 답이 질문 샘플에서 나온다. 모호한 것만 명시적으로 묻는다.

한 번에 확인이 안 되면 모름으로 두고 진행한다. 다만 **접근 제어(4번)와 오답 비용(5번)은 반드시 답을 받는다.** 이 둘은 나중에 붙이는 비용이 재설계 수준으로 크다.

## 답변 → 설계 매핑

### 1. 질문 유형

| 유형 | 예시 | 설계 영향 |
|---|---|---|
| 단일 사실 조회 | "연차는 며칠인가요" | 작은 청크(256~512), top-k 작게(3~5), 리랭커 효과 큼 |
| 절차 안내 | "휴직 신청 어떻게 하나요" | 절차가 잘리면 답이 망가진다 → 큰 청크 또는 parent-child |
| 요약·종합 | "작년 보안 이슈 정리해줘" | top-k 크게(10~20), 컨텍스트 예산 크게, 비용 상승 |
| 비교·분석 | "A정책과 B정책 차이" | multi-hop — 쿼리 분해 필요, 베이스라인으로는 잘 안 된다 |

주력 유형이 둘 이상이면 **의도 분류기를 앞단에 두고 경로를 나누는 것**이 보통 단일 파이프라인 튜닝보다 싸게 먹힌다.

### 2. 코퍼스

- **문서 수 < 1,000, 총 100MB 이하** → 벡터 DB 고민할 단계 아니다. 인메모리나 pgvector로 충분. 인프라 선택에 시간 쓰지 말 것.
- **스캔 PDF·이미지 기반** → OCR 품질이 상한선을 정한다. 여기가 나쁘면 뒷단 전부 무의미하므로 파싱 검증을 Step 1과 병행한다.
- **표가 핵심 정보** → 일반 텍스트 추출은 표를 뭉갠다. 표는 별도로 뽑아 마크다운으로 저장하고, 표 단위를 하나의 청크로 유지한다.
- **갱신 주기가 짧음(일 단위)** → 증분 인덱싱 설계 필요. `references/operations.md` 참고.
- **다국어 / 한국어** → 임베딩 모델 선택이 좁아진다. `references/retrieval.md` 참고.

### 3. 정답의 소재

이걸 확인하는 가장 빠른 방법: 받은 실제 질문 10개에 **직접 답을 찾아본다.** 한 문단에서 답이 나오는지, 문서 3개를 열어야 하는지가 즉시 드러난다.

multi-hop이 주력이면 베이스라인 RAG는 실패한다. 설계 문서에 이것을 위험으로 먼저 적고, 쿼리 분해를 Step 2에 포함시킨다.

### 4. 접근 제어

"사용자 A는 인사 문서를 볼 수 있고 B는 못 본다"가 있으면:

- 권한 태그를 **청크 메타데이터에 넣고**, 검색 시 필터를 **사전 필터(pre-filter)로** 적용한다. 검색 후 걸러내면(post-filter) top-k가 줄어들어 recall이 무너진다.
- 벡터 스토어 선택이 여기서 제약된다 — 메타데이터 필터링을 효율적으로 지원하는지 확인.
- 평가도 권한별로 나눠야 한다. 전체 코퍼스 기준 recall은 의미가 없다.

### 5. 오답 비용

| 수준 | 예 | 설계 요구 |
|---|---|---|
| 낮음 | 사내 위키 Q&A | 인용 표시 권장 |
| 중간 | 고객 지원 1차 응대 | 인용 필수, 신뢰도 낮으면 상담원 연결 |
| 높음 | 법률·의료·금융·규정 해석 | 인용 필수 + abstain 정책 + 사람 검토 + 답변 로그 보존 |

높음이면 "모르겠습니다"의 비율이 **품질 지표**가 된다. 낮을수록 좋은 게 아니다.

### 6. 예산

- p95 지연 목표를 먼저 받고, 리랭커(+100~300ms)와 쿼리 재작성(+1 LLM 호출)을 그 예산에 넣을 수 있는지 계산한다.
- 월 쿼리 수 × 쿼리당 토큰으로 비용을 개략 계산해 설계 문서에 적는다. `references/generation.md`에 모델별 단가표.
- 예산이 빡빡하면 리랭커보다 **top-k 축소**가 먼저다. 품질 손실 대비 이득이 크다.

### 7. 현재 상태

개선 프로젝트라면 실패 사례 10개에 대해 **현재 파이프라인의 검색 결과를 덤프해서 함께 본다.** 대부분 이 단계에서 원인이 보인다 — 파싱이 깨졌거나, 질문 용어가 문서 용어와 다르거나, 청크가 답을 가운데서 잘랐거나.

## 설계 카드

각 결정을 이 형식으로 기록한다. 설계 문서의 기본 단위다.

```
결정: 청크 크기 512 토큰 / 오버랩 15%
근거: 문단 평균 380 토큰, 절차 설명이 2~3문단에 걸침
대안: 1024(절차 보존 유리, precision 하락) / 256(정밀하지만 절차 잘림)
측정: context_recall, context_precision
재검토: recall < 0.85 이면 1024 + parent-child 재시도
```

근거를 못 쓰겠으면 아직 결정할 단계가 아니다. 기본값으로 두고 측정 후에 돌아온다.
