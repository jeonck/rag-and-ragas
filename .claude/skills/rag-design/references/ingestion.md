# 수집·청킹·인덱싱

검색이 못 찾는 문서는 대개 임베딩이 나빠서가 아니라 **청크가 잘못 잘려서**다. 이 단계의 오류는 뒷단 전체의 상한선이 된다.

## 1. 파싱

### 확인 순서

1. 문서 5개를 파싱해서 **결과 텍스트를 직접 읽는다.** 자동화 전에 눈으로 본다.
2. 표·각주·머리말/꼬리말·목차가 어떻게 나왔는지 본다.
3. 깨진 게 있으면 파서를 바꾼다. 여기서 타협하면 뒤에서 회수할 수 없다.

### 형식별

| 형식 | 기본 접근 | 함정 |
|---|---|---|
| 텍스트 PDF | 텍스트 추출 + 레이아웃 보존 | 2단 조판이 줄 단위로 섞인다. 반드시 확인 |
| 스캔 PDF | OCR | OCR 품질이 전체 상한. 한국어면 특히 검증 필요 |
| HTML | 본문 추출(boilerplate 제거) | 네비게이션·푸터가 모든 청크를 오염시킨다 |
| 표 | 마크다운 표로 별도 추출 | 일반 추출은 셀 경계를 잃는다. 표는 표로 |
| 코드·설정 | 원문 그대로, 언어 태그 유지 | 토크나이저가 코드에서 토큰을 많이 먹는다 |
| 슬라이드 | 슬라이드=청크, 발표자 노트 포함 | 도표만 있는 슬라이드는 텍스트가 거의 없다 |

### 머리말/꼬리말 제거

페이지마다 반복되는 문자열("사내기밀", 페이지 번호, 문서 제목)은 제거한다. 남겨두면 모든 청크의 임베딩이 그쪽으로 끌려가 유사도가 뭉개진다. 빈도 기반으로 반복 라인을 찾아 지우는 것이 간단하고 잘 듣는다.

## 2. 청킹

### 기본값

**512 토큰, 15% 오버랩, 문단 경계 우선.** 여기서 시작해서 recall을 보고 조정한다.

경계 우선순위: 문서 섹션 > 문단 > 문장 > 토큰. 문장 중간에서 자르는 일은 없어야 한다.

### 전략 비교

| 전략 | 방식 | 맞는 상황 | 대가 |
|---|---|---|---|
| 고정 크기 | N 토큰 + 오버랩 | 기본. 대부분 여기서 충분 | 의미 단위를 가를 수 있음 |
| 구조 기반 | 마크다운 헤딩·섹션 단위 | 구조가 일관된 매뉴얼·규정집 | 섹션 길이 편차가 크면 청크 크기가 널뜀 |
| Parent-child | 작은 청크로 검색, 부모 문단을 컨텍스트로 전달 | 절차·설명형. 정밀 검색과 충분한 문맥을 동시에 | 저장·구현 복잡도 증가 |
| 문서 1개 = 1청크 | 분할 없음 | 짧은 FAQ, 짧은 정책 | 문서가 길면 precision 붕괴 |
| 시맨틱 청킹 | 문장 임베딩 유사도가 꺾이는 지점에서 분할 | 구조가 없는 산문 | 인덱싱 비용 큼, 이득이 작은 경우가 많음 — 베이스라인 실패 후에 |

**시맨틱 청킹은 기본값이 아니다.** 비용 대비 개선폭이 데이터에 크게 의존한다. 고정 크기로 측정한 뒤 비교하고 선택한다.

### 오버랩

경계에서 잘린 정보를 살리는 보험이다. 15%면 대개 충분하다. 50%까지 올리면 저장량과 중복 검색이 늘어 precision이 떨어진다.

### 청크 크기를 정하는 법

회의가 아니라 측정으로 정한다. 골든셋이 있으면 30분이면 된다.

```
256 / 512 / 1024 세 가지로 인덱스를 만들고
같은 골든셋으로 context_recall, context_precision을 잰다.
recall이 크게 다르지 않으면 작은 쪽을 택한다 (비용·precision 유리).
```

## 3. 청크 보강

검색 품질을 올리는 가장 값싼 수단은 청크 자체를 더 검색되기 좋게 만드는 것이다.

- **컨텍스트 헤더 붙이기** — 각 청크 앞에 `문서 제목 > 섹션 제목`을 붙인다. "3항의 경우 30일 이내"만 있는 청크는 검색이 불가능하지만, `취업규칙 > 휴직 > 3항의 경우 30일 이내`는 찾힌다. 구현 비용 대비 효과가 가장 큰 기법 중 하나다.
- **표에 캡션 붙이기** — 표 청크 앞에 표가 무엇에 대한 것인지 한 줄.
- **약어·동의어 확장** — 사내 약어가 많으면 용어 사전을 만들어 청크나 쿼리 쪽에서 확장한다. 어느 쪽이든 한쪽만 한다.

## 4. 메타데이터 스키마

인덱싱 시점에 확정한다. 나중에 추가하려면 전체 재인덱싱이다.

```
doc_id          원본 문서 식별자 (인용·원문 링크용)
chunk_id        청크 식별자
title           문서 제목
section         섹션 경로 ("휴직 > 육아휴직")
source_uri      원본 위치 (사용자가 클릭해서 확인할 수 있어야 한다)
created_at      문서 작성일
updated_at      최종 수정일 (최신성 필터·정렬용)
acl             접근 권한 태그 (접근 제어가 있으면 필수)
doc_type        정책 / 매뉴얼 / FAQ / 회의록 ...
lang            언어
```

`updated_at`과 `acl`은 특히 나중에 붙이기 어렵다. 필요 없을 것 같아도 넣어둔다.

## 5. 인덱싱

- **BM25 인덱스와 벡터 인덱스를 함께 만든다.** 하이브리드는 나중에 켜더라도 인덱스는 처음부터 둘 다 만들어 두는 편이 싸다.
- **중복 제거** — 같은 내용이 여러 문서에 복붙된 경우가 흔하다. 중복 청크는 top-k를 잡아먹어 precision을 깎는다. 해시나 근사 중복 탐지로 인덱싱 시점에 정리한다.
- **버전 관리** — 문서가 개정되면 옛 청크를 지운다. 안 지우면 시스템이 구 규정과 신 규정을 함께 검색해 모순된 답을 만든다. 실무에서 아주 흔한 사고다.
- **인덱싱 로그** — 문서별 청크 수, 평균 길이, 파싱 실패 건수를 남긴다. 청크가 1개만 나온 긴 문서는 파싱 실패 신호다.

## 6. 검수

인덱싱이 끝나면 **무작위 청크 20개를 읽는다.** 자동화할 수 없는 단계이고, 생략하면 나중에 훨씬 비싸게 발견한다. 볼 것:

- 문장이 중간에서 잘렸는가
- 표가 뭉개졌는가
- 머리말/꼬리말 잔재가 있는가
- 이 청크만 보고 무슨 문서의 어느 부분인지 알 수 있는가 (모르면 컨텍스트 헤더가 필요하다)
