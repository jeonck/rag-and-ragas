# 검색

RAG 실패의 대부분이 여기서 난다. 생성 모델을 바꾸기 전에 이 문서를 먼저 본다.

## 1. 임베딩 모델

### 선택 기준

1. **언어** — 한국어가 포함되면 다국어 모델이어야 한다. 영어 전용 모델은 한국어에서 급격히 나빠진다.
2. **최대 입력 길이** — 청크 크기보다 커야 한다. 512 토큰 모델에 1024 토큰 청크를 넣으면 뒤가 잘린다. 조용히 잘리기 때문에 발견이 늦다.
3. **차원 수** — 저장·검색 비용에 직결. 1024 이상이 항상 좋은 건 아니다.
4. **셀프 호스팅 가능 여부** — 데이터 반출 제약이 있으면 여기서 후보가 결정된다.

### 실무 후보

| 모델 | 특징 |
|---|---|
| `BAAI/bge-m3` | 다국어(한국어 양호), 8192 토큰, 셀프 호스팅, dense+sparse 동시 지원 |
| `intfloat/multilingual-e5-large` | 다국어, 안정적, 512 토큰 제한에 주의 |
| Voyage (voyage-3 계열) | API형, 검색 특화, 성능 좋음 |
| 도메인 특화 모델 | 의료·법률 등 전문 코퍼스에서 범용 모델이 밀릴 때 |

**주의: Anthropic은 임베딩 API를 제공하지 않는다.** 임베딩은 별도 제공자나 셀프 호스팅 모델을 쓴다.

### 비대칭 검색

질문과 문서는 길이·어투가 다르다. e5 계열처럼 `query:` / `passage:` 접두어를 요구하는 모델은 반드시 지켜야 한다. 안 붙이면 성능이 눈에 띄게 떨어지는데 에러는 안 난다.

### 모델 교체는 재인덱싱이다

임베딩 모델을 바꾸면 전체를 다시 임베딩해야 한다. 코퍼스가 크면 비용이 크므로, 바꾸려면 **골든셋으로 소규모 샘플 비교를 먼저** 한다.

## 2. 벡터 스토어

대부분의 프로젝트에서 이건 중요한 결정이 아니다. 시간을 많이 쓰지 말 것.

| 규모 | 선택 |
|---|---|
| ~10만 청크 | pgvector (이미 Postgres를 쓴다면 압도적으로 편하다), 또는 인메모리 |
| ~1천만 청크 | Qdrant, Weaviate, Milvus 등 전용 엔진 |
| 관리형 선호 | Pinecone 등 |

실제로 봐야 할 것: **메타데이터 사전 필터링 성능**, 증분 upsert·삭제 지원, 하이브리드 검색 내장 여부.

## 3. 하이브리드 검색

벡터 검색은 의미가 비슷한 걸 찾고, BM25는 정확한 문자열을 찾는다. 둘 다 필요하다.

BM25가 특히 중요한 경우:
- 고유명사, 제품명, 사람 이름
- 에러 코드, 법 조항 번호, 사번 같은 식별자
- 약어
- 오타 없는 정확한 용어로 검색하는 전문가 사용자

벡터가 강한 경우: 사용자가 문서와 다른 표현으로 묻는 경우, 개념적 질문.

### 결합 방법

**RRF(Reciprocal Rank Fusion)**가 기본값이다. 점수 정규화가 필요 없고 가중치 튜닝 없이도 잘 듣는다.

```
score(d) = Σ_i  1 / (k + rank_i(d))       # k는 보통 60
```

점수 가중합(alpha 튜닝)은 RRF로 먼저 측정한 뒤, 개선 여지가 보일 때만 간다.

## 4. 쿼리 변환

원 질문을 그대로 검색하는 것이 항상 최선은 아니다. 단, **하나씩 추가하고 측정한다.** 전부 켜면 지연과 비용만 늘고 이득은 불분명해진다.

| 기법 | 방식 | 언제 |
|---|---|---|
| 쿼리 재작성 | LLM이 검색용 질의로 다듬음 | 대화형 후속 질문("그럼 그건요?")이 많을 때 — 이 경우는 사실상 필수 |
| 쿼리 분해 | 복합 질문을 하위 질문으로 쪼개 각각 검색 | multi-hop·비교 질문 |
| 다중 질의 | 같은 질문을 여러 표현으로 확장해 합집합 검색 | recall이 낮고 용어 불일치가 원인일 때 |
| HyDE | 가상의 답변을 생성해 그 임베딩으로 검색 | 질문이 짧고 문서가 서술형일 때. 비용 대비 이득은 편차가 크다 |
| 메타데이터 추출 | 질문에서 기간·부서 등을 뽑아 필터로 | "작년 4분기" 같은 조건이 자주 나올 때 |

대화형 서비스라면 **쿼리 재작성은 선택이 아니다.** 대명사와 생략이 섞인 후속 질문은 그대로 검색하면 반드시 실패한다.

## 5. 리랭킹

1차 검색은 빠르지만 거칠다. 20개를 가져와 cross-encoder로 다시 점수 매겨 상위 5개만 생성에 넘긴다.

- 1차 top-k: 20 (recall 확보)
- 리랭크 후: 3~5 (precision 확보)
- 지연: 보통 +100~300ms

**리랭커는 precision을 올리지 recall을 올리지 않는다.** 1차 검색이 정답을 아예 못 가져왔으면 리랭커는 아무것도 못 한다. `context_recall`이 낮으면 리랭커 도입은 답이 아니다.

지연 예산이 없으면 리랭커를 빼고 top-k를 5로 줄인다. 그게 top-k 20을 그냥 다 넣는 것보다 낫다.

## 6. 메타데이터 필터

- **접근 제어는 반드시 사전 필터.** 검색 후에 걸러내면 top-k가 줄어 recall이 무너지고, 사용자마다 결과 품질이 달라진다.
- **최신성** — 개정이 잦은 문서는 `updated_at` 필터나 최신 우선 가중치를 건다. 구 버전과 신 버전이 함께 검색되면 모순된 답이 나온다.
- **문서 종류** — 질문 의도에 따라 `doc_type`을 제한하면 노이즈가 크게 준다.

## 7. top-k 정하기

| 질문 유형 | 리랭크 후 k |
|---|---|
| 단일 사실 조회 | 3 |
| 절차 안내 | 5 |
| 요약·종합 | 10~20 |

k를 키우면 recall은 오르고 precision은 떨어진다. 컨텍스트가 크다고 무작정 늘리지 않는다 — 노이즈는 정확도를 떨어뜨린다.

## 8. 검색 단계 점검

`context_recall`이 낮을 때 순서대로 확인한다.

1. **정답 청크가 인덱스에 있는가** — 없으면 파싱·청킹 문제다. `ingestion.md`로 간다.
2. **정답 청크를 ID로 직접 조회하면 내용이 온전한가** — 잘렸으면 청킹 문제.
3. **질문 용어와 청크 용어가 다른가** — 약어·동의어 문제. 용어 확장이나 하이브리드 비중 조정.
4. **BM25 단독으로는 찾히는가** — 찾히면 하이브리드를 켜거나 BM25 비중을 올린다.
5. **top-k를 50으로 늘리면 들어오는가** — 들어오면 랭킹 문제(리랭커), 안 들어오면 임베딩·인덱스 문제.

이 5단계로 대부분의 검색 실패는 원인이 특정된다.
