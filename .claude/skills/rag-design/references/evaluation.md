# 평가 — 골든셋과 RAGAS

이 문서의 목적은 하나다. **"좋아진 것 같다"를 "recall 0.72 → 0.86"으로 바꾸는 것.**

## 1. 골든셋

### 규모와 구성

최소 30문항, 권장 50문항. 그 이상 늘리는 것보다 **구성의 다양성**이 중요하다.

| 구성 | 비율 | 이유 |
|---|---|---|
| 실제 사용자 질문 | 50% 이상 | 실제 분포를 반영해야 의미가 있다 |
| 답이 코퍼스에 없는 질문 | 10~20% | 이게 없으면 할루시네이션을 측정할 수 없다 |
| 여러 문서 종합(multi-hop) | 10~20% | 베이스라인의 한계가 드러나는 지점 |
| 파싱 취약부(표·각주·부록) | 10% | 조용히 깨져 있는 곳을 잡아낸다 |
| 약어·오타·구어체 | 10% | 실제 입력은 정갈하지 않다 |

### 항목 형식

`assets/` 없이 JSONL 한 줄이면 충분하다.

```json
{"question": "육아휴직은 최대 며칠까지 쓸 수 있나요?",
 "ground_truth": "자녀 1명당 최대 1년(365일)입니다.",
 "reference_chunk_ids": ["hr-rules-2024#sec4.2"],
 "tags": ["single-hop", "policy"]}
```

`reference_chunk_ids`가 있으면 LLM 판정 없이도 recall을 직접 계산할 수 있다. 가능하면 넣는다 — 빠르고 싸고 결정적이다.

답이 없는 질문은 `ground_truth`를 "코퍼스에 정보 없음"으로 두고 `tags`에 `unanswerable`을 붙인다.

### 만드는 법

1. **실제 로그가 있으면 거기서 뽑는다.** 가장 좋은 출처다.
2. **없으면 도메인 담당자에게 받는다.** "사람들이 자주 묻는 것 20개"를 요청한다.
3. **LLM 합성은 보조로만.** 문서를 주고 질문을 생성시키면 빠르게 수를 채울 수 있지만, 생성된 질문은 문서의 표현을 그대로 쓰는 경향이 있어 **검색을 실제보다 쉽게 만든다.** 합성 문항만으로 된 골든셋은 실전 recall을 과대평가한다. 합성을 쓴다면 표현을 바꾸는 단계를 거치고, 실제 질문과 비율을 나눠 점수를 따로 본다.
4. **정답은 사람이 확인한다.** 여기서 타협하면 이후 모든 측정이 흔들린다.

### 분할

골든셋을 `dev`(튜닝용)와 `holdout`(최종 확인용)으로 나눈다. dev만 보고 계속 튜닝하면 그 30문항에 과적합된 파이프라인이 나온다. holdout은 큰 변경 후에만 본다.

## 2. RAGAS 지표

### 4개의 핵심 지표

| 지표 | 계산에 필요한 것 | 낮으면 |
|---|---|---|
| **context_recall** | 질문, 검색결과, 정답 | 검색이 근거를 못 가져옴 → 검색/청킹 |
| **context_precision** | 질문, 검색결과, 정답 | 관련 없는 것이 상위에 → 랭킹/리랭커 |
| **faithfulness** | 질문, 검색결과, 답변 | 답이 컨텍스트를 벗어남 → 생성/프롬프트 |
| **answer_relevancy** | 질문, 답변 | 질문에 안 답함 → 프롬프트/의도 이해 |

**반드시 4개를 함께 본다.** faithfulness만 올리면 "모르겠습니다"만 하는 시스템이 만점을 받는다. answer_relevancy만 올리면 그럴듯하게 지어낸다. 이 지표들은 서로를 견제하도록 설계돼 있다.

### 검색 실패와 생성 실패의 분리

이게 RAGAS를 쓰는 가장 큰 이유다.

- `context_recall`이 낮고 `faithfulness`는 높다 → 검색이 문제다. 모델을 바꿔도 소용없다.
- `context_recall`은 높은데 `faithfulness`가 낮다 → 근거를 줬는데 안 쓰고 있다. 프롬프트 문제다.

이 구분 없이 튜닝하면 대개 엉뚱한 쪽을 고친다.

### 보조 지표

- `FactualCorrectness` — 답변과 정답의 사실 일치. 정답 문장이 확실할 때 유용.
- `NoiseSensitivity` — 관련 없는 컨텍스트가 섞였을 때 답이 흔들리는 정도. top-k를 키울지 결정할 때.

처음부터 다 쓰지 않는다. 4개로 시작한다.

## 3. 판정 모델

RAGAS 지표 대부분은 LLM이 판정한다(LLM-as-judge). 따라서:

- **판정 모델은 고정한다.** 중간에 바꾸면 이전 점수와 비교 불가능해진다. 설계 문서에 판정 모델 ID를 적어 둔다.
- 판정 모델은 기본적으로 `claude-opus-5`를 쓴다. 비용이 문제면 `claude-sonnet-5`로 내리되, **한 번 정하면 유지한다.**
- 일부 지표(`answer_relevancy`, 의미 유사도)는 임베딩 모델도 필요하다. 이것도 고정한다.
- 판정에도 변동성이 있다. 점수 차이가 0.02 수준이면 개선이라고 부르지 않는다. 의미 있는 변화의 폭을 초기에 정해 둔다(보통 0.05 이상).

## 4. 실행

`scripts/ragas_eval.py`를 쓴다.

```bash
python scripts/ragas_eval.py \
  --golden data/golden.jsonl \
  --pipeline myapp.rag:answer \
  --out results/run-$(date +%Y%m%d-%H%M).json
```

`--pipeline`은 `모듈:함수` 형식이며, 함수는 질문 문자열을 받아 `{"answer": str, "contexts": list[str]}`를 반환하면 된다. 이미 실행 결과가 있으면 `--predictions`로 JSONL을 바로 넣을 수도 있다.

임계치 미달이면 exit code 1을 반환하므로 CI에 그대로 붙일 수 있다.

### RAGAS 버전 주의

RAGAS는 마이너 버전 사이에서 API가 바뀐 이력이 있다(`Dataset` 기반 → `EvaluationDataset`/`SingleTurnSample`, 지표 클래스명 변경 등). 따라서:

- **버전을 핀으로 고정한다** (`ragas==x.y.z`). 설계 문서에도 적는다.
- 스크립트를 처음 돌리기 전에 `python -c "import ragas; print(ragas.__version__)"`로 확인하고, import 에러가 나면 설치된 버전의 문서를 확인한다. 기억에 의존해서 고치지 말 것.

## 5. 회귀 방지

측정을 한 번 하고 끝내면 아무 의미가 없다. 파이프라인이 바뀔 때마다 돌아야 한다.

- 인덱싱 설정, 프롬프트, 모델, top-k — **하나라도 바뀌면 평가를 돌린다.**
- 임계치를 CI 게이트로 건다. 초기 목표: recall 0.85 / precision 0.70 / faithfulness 0.90 / relevancy 0.85.
- 결과를 커밋 해시와 함께 저장한다. 3개월 뒤 "언제부터 나빠졌나"를 답할 수 있어야 한다.
- 지표가 아니라 **개별 문항 단위 변화**도 본다. 평균은 같은데 절반이 좋아지고 절반이 나빠졌을 수 있다.

## 6. 지표가 놓치는 것

RAGAS는 만능이 아니다. 다음은 따로 봐야 한다.

- **지연과 비용** — 지표에 안 잡힌다. 매 실행마다 p95 지연과 쿼리당 토큰을 함께 기록한다.
- **답변의 유용성** — 사실 정확하지만 쓸모없는 답이 있다. 정기적으로 사람이 표본을 읽는다.
- **실패의 체감 심각도** — "약간 부정확"과 "정반대로 안내"는 지표상 비슷하게 보일 수 있다. 오답 비용이 높은 도메인이면 실패 사례를 등급으로 분류한다.

지표는 방향을 알려주지 결론을 내주지 않는다. **매 라운드 실패 문항 5개는 직접 읽는다.**
