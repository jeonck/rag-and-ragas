# 운영

설계 문서에 반드시 들어가야 하는데 자주 빠지는 것들.

## 1. 인덱스 갱신

### 증분 인덱싱

문서가 바뀔 때마다 전체 재인덱싱은 현실적이지 않다. 문서 단위 upsert·삭제를 설계에 넣는다.

- 문서 해시를 저장해 **바뀐 것만** 다시 처리한다.
- 문서가 수정되면 그 문서의 **기존 청크를 먼저 지우고** 새로 넣는다. 안 지우면 구 버전이 계속 검색된다 — RAG에서 가장 흔한 운영 사고다.
- 삭제된 문서는 인덱스에서도 삭제한다. 접근 권한이 회수된 문서가 계속 답변에 인용되는 것은 보안 사고다.

### 전체 재인덱싱이 필요한 경우

임베딩 모델 교체, 청킹 전략 변경, 메타데이터 스키마 변경. 이건 계획된 작업으로 다룬다 — 소요 시간과 비용을 미리 계산하고, 블루/그린으로 새 인덱스를 만든 뒤 골든셋 평가를 통과하면 전환한다.

## 2. 모니터링

지표 대시보드보다 **로그가 먼저**다. 쿼리별로 남긴다.

```
timestamp, user_id(또는 해시), 원 질문, 재작성된 질의,
검색된 chunk_id + 점수, 리랭크 후 chunk_id,
최종 답변, 인용 목록, abstain 여부,
지연(단계별), 토큰 사용량
```

이게 있으면 사후에 어떤 실패든 재구성할 수 있다. 없으면 "가끔 이상해요" 제보에 아무 대응도 못 한다.

### 볼 지표

| 지표 | 왜 |
|---|---|
| abstain 비율 | 급등하면 인덱스나 검색이 망가진 신호 |
| 평균 검색 최고 점수 | 하락 추세면 코퍼스와 질문 분포가 벌어지고 있다 |
| 인용 0개 답변 비율 | 근거 없이 답하는 비율. 0에 가까워야 한다 |
| p95 지연 (단계별) | 어느 단계가 느린지 분리해서 본다 |
| 쿼리당 비용 | 예산 이탈을 조기에 잡는다 |
| 사용자 피드백(👍/👎) | 적은 수라도 실패 사례 수집 창구로 값지다 |

### 실패 사례 수집

👎를 누른 쿼리는 자동으로 큐에 쌓아 정기적으로 검토하고, 재현되는 것은 **골든셋에 추가한다.** 골든셋은 정적인 문서가 아니라 자라는 자산이다.

## 3. 캐싱

세 층이 있고 각각 다른 문제를 푼다.

- **응답 캐시** — 동일 질문에 동일 답. FAQ성 질문이 반복되는 서비스에서 효과가 크다. 코퍼스가 갱신되면 무효화해야 한다.
- **검색 결과 캐시** — 같은 질의의 검색 결과 재사용. 인덱스 변경 시 무효화.
- **프롬프트 캐시** — 시스템 프롬프트·고정 문서. `generation.md` 참고.

응답 캐시는 **권한별로 분리**해야 한다. 사용자 A의 답이 B에게 나가면 사고다.

## 4. 보안

- **접근 제어는 검색 단계의 사전 필터로.** 생성 단계나 UI에서 거르는 설계는 안 된다.
- **PII** — 코퍼스에 개인정보가 있으면 인덱싱 전에 마스킹할지 결정한다. 인덱싱 후에는 벡터에도 흔적이 남아 제거가 번거롭다.
- **프롬프트 주입** — 코퍼스 문서 자체에 지시문이 들어 있을 수 있다(외부에서 수집한 문서라면 특히). 검색된 문서는 데이터이지 지시가 아님을 시스템 프롬프트에서 명시하고, 문서 블록을 명확한 경계로 감싼다.
- **로그의 민감도** — 질문과 답변에 민감 정보가 담긴다. 보존 기간과 접근 권한을 정한다.

## 5. 롤아웃

1. **내부 사용자 소수**로 시작한다. 실패 사례를 빠르게 모으는 게 목적이다.
2. **abstain을 넉넉하게** 설정해서 시작한다. 초기에 틀린 답을 많이 내는 것보다 "모르겠다"가 많은 편이 신뢰 확보에 낫다. 익숙해지면 조인다.
3. **인용 UI를 1일차부터** 넣는다. 나중에 붙이는 기능이 아니다.
4. **대조군 유지** — 기존 검색 시스템이 있으면 병행 운영하며 비교한다.

## 6. 문서화해 둘 것

운영 인수인계에서 빠지면 곤란한 것들.

- 임베딩 모델 ID와 버전 (재인덱싱 시 필요)
- 청킹 파라미터
- RAGAS 판정 모델 ID와 RAGAS 버전 핀
- 골든셋 위치와 마지막 평가 결과
- 재인덱싱 절차와 소요 시간
- 임계치와 그 근거
