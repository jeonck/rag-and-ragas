# 생성

검색이 정답 문서를 가져왔다는 전제에서, 답을 만드는 단계의 설계.

## 1. 컨텍스트 구성

### 배치 순서

```
[시스템 프롬프트 — 역할, 규칙, 인용 정책]        ← 고정. 캐시 대상
[검색된 문서 블록들 — 각각 출처 메타데이터 포함]  ← 쿼리마다 변함
[대화 이력]
[사용자 질문]
```

- **문서는 질문보다 앞에.** 질문을 마지막에 두면 모델이 무엇을 찾아야 하는지 알고 문서를 읽는 효과가 난다.
- **문서마다 출처를 붙인다.** `[문서 3: 취업규칙 > 휴직, 2024-03-01 개정]` 같은 헤더. 인용을 요구하려면 인용할 이름이 있어야 한다.
- **순서에 의미를 두지 않는다.** 리랭킹 점수 순으로 넣되, 모델에게 "앞의 것이 더 중요하다"고 말하지 않는다. 관련성 판단은 모델에게 맡기는 편이 낫다.

### 컨텍스트 예산

1M 컨텍스트가 있어도 검색 결과를 다 넣지 않는다. 노이즈는 정확도를 떨어뜨리고 비용은 선형으로 는다. 리랭크 후 3~5개가 기본이다.

## 2. 프롬프트 템플릿

```
당신은 <조직>의 <문서 종류>를 근거로 답하는 어시스턴트입니다.

규칙:
- 제공된 문서에 있는 내용만으로 답합니다. 일반 지식으로 보충하지 않습니다.
- 모든 사실 주장에 근거 문서를 표시합니다.
- 문서에 답이 없으면 "제공된 문서에서 확인할 수 없습니다"라고 답하고,
  관련이 있을 만한 문서가 있으면 무엇을 봤는지 알려줍니다.
- 문서들이 서로 모순되면 모순을 지적하고 각각의 출처와 날짜를 밝힙니다.
- 추측을 답처럼 쓰지 않습니다.
```

마지막 두 줄이 실무에서 특히 중요하다. 개정 전후 문서가 함께 검색되는 일이 잦은데, 모순을 지적하지 않는 시스템은 조용히 틀린 답을 낸다.

### 모른다고 답하게 만들기

할루시네이션 대책의 핵심이다. 규칙만으로 부족하면:

- 골든셋에 **답이 없는 질문**을 넣고 faithfulness와 abstain 정확도를 함께 측정한다.
- 검색 점수가 임계치 미만이면 생성 단계를 아예 건너뛰고 정해진 문구를 반환한다. LLM에게 맡기는 것보다 확실하다.
- 오답 비용이 높은 도메인에서는 abstain 비율이 낮은 게 좋은 게 아니다.

## 3. 인용

프롬프트로 `[1]` 마커를 요구하는 방식은 모델이 번호를 잘못 붙이는 일이 흔하다. Claude를 쓴다면 **Citations 기능**을 쓴다 — API가 인용 범위를 직접 표시하므로 번호가 틀어지지 않는다.

각 document 블록에 `citations: {enabled: true}`를 켠다(전부 켜거나 전부 끄거나, 섞으면 안 된다). 검색된 청크는 custom content 문서 형태로 넣는 게 자연스럽다.

```python
import anthropic

client = anthropic.Anthropic()

documents = [
    {
        "type": "document",
        "source": {
            "type": "content",
            "content": [{"type": "text", "text": chunk["text"]}],
        },
        "title": f'{chunk["title"]} > {chunk["section"]}',
        "context": f'출처: {chunk["source_uri"]} (개정 {chunk["updated_at"]})',
        "citations": {"enabled": True},
    }
    for chunk in retrieved_chunks
]

response = client.messages.create(
    model="claude-opus-5",
    max_tokens=16000,
    system=SYSTEM_PROMPT,
    messages=[{"role": "user", "content": [*documents, {"type": "text", "text": question}]}],
)
```

응답의 `content`는 여러 `text` 블록으로 쪼개져 오고, 근거가 있는 블록에는 `citations` 배열이 붙는다. 각 인용에는 `cited_text`, `document_index`, `document_title`과 위치 정보(custom content면 `content_block_location`, PDF면 `page_location`, 평문이면 `char_location`)가 들어 있다. 이걸 그대로 UI의 출처 링크로 쓰면 된다.

**제약 하나:** Citations는 구조화 출력(`output_config.format`)과 함께 쓸 수 없다(400). 답변을 JSON 스키마로 강제하면서 동시에 인용을 받을 수는 없으므로, 설계 시점에 어느 쪽이 필요한지 정한다. 대부분의 RAG는 인용이 더 중요하다.

## 4. 모델 선택

| 모델 | ID | 컨텍스트 | 입력 $/1M | 출력 $/1M |
|---|---|---|---|---|
| Claude Opus 5 | `claude-opus-5` | 1M | $5.00 | $25.00 |
| Claude Sonnet 5 | `claude-sonnet-5` | 1M | $2.00 | $10.00 |
| Claude Haiku 4.5 | `claude-haiku-4-5` | 200K | $1.00 | $5.00 |

기본은 `claude-opus-5`. 비용 때문에 낮추는 것은 **사용자가 결정할 문제**이지 설계자가 임의로 내릴 일이 아니다. 낮추려면 골든셋으로 faithfulness·answer_relevancy를 비교해 손실을 수치로 보여주고 정한다.

경로를 나누는 방식이 흔히 유효하다 — 단순 조회는 저렴한 모델, 종합·분석 질문은 상위 모델.

### 요청 파라미터

- **thinking**: 기본은 `{"type": "adaptive"}`(생략해도 Opus 5는 적응형으로 동작). `budget_tokens`는 현행 모델에서 제거되어 400을 반환한다.
- **effort**: `output_config: {"effort": "low"|"medium"|"high"|"xhigh"|"max"}`. 기본 `high`. 단순 조회형 RAG는 `low`~`medium`으로 충분한 경우가 많고 비용이 눈에 띄게 준다. 라우트별로 따로 튜닝한다.
- **max_tokens**: 비스트리밍이면 16000 근처, 스트리밍이면 크게. 낮게 잡아 중간에 잘리는 것이 흔한 사고다.
- **스트리밍**: 사용자 대면 챗이면 필수. 첫 토큰까지의 시간이 체감 품질을 좌우한다.
- **assistant prefill은 현행 모델에서 400이다.** 출력 형식 제어는 시스템 프롬프트나 구조화 출력으로 한다.

## 5. 프롬프트 캐싱

RAG에서 캐싱이 듣는 곳과 안 듣는 곳이 갈린다. 캐시는 **접두사 일치**라서, 한 바이트라도 바뀌면 그 뒤가 전부 무효가 된다. 렌더 순서는 `tools` → `system` → `messages`.

- **캐시 대상**: 고정 시스템 프롬프트, 도구 정의, 모든 쿼리에 항상 붙는 문서(용어집, 정책 요약 등).
- **캐시 대상 아님**: 검색된 청크. 쿼리마다 달라지므로 마지막 캐시 breakpoint **뒤에** 둔다.
- 최소 캐시 가능 길이가 모델별로 512~4096 토큰이다. 시스템 프롬프트가 짧으면 캐시가 조용히 안 걸린다.
- 확인 방법: `usage.cache_read_input_tokens`가 반복 요청에서 계속 0이면 무언가가 접두사를 흔들고 있다(타임스탬프, 정렬 안 된 JSON, 매번 바뀌는 도구 목록).

멀티턴 대화 RAG라면 시스템 프롬프트 캐싱만으로도 비용이 의미 있게 준다.

## 6. 출력 설계

- **답변 + 출처 목록**을 분리해 UI에 노출한다. 사용자가 검증할 수 없는 답은 신뢰를 못 얻는다.
- **신뢰도 신호**를 넘긴다 — 검색 점수, 인용 개수, abstain 여부. 프론트에서 경고 배지를 띄울 근거가 된다.
- **로깅**: 질문, 재작성된 질의, 검색된 chunk_id 목록과 점수, 최종 답, 인용. 이게 없으면 사후에 실패 원인을 못 찾는다. 오답 비용이 높은 도메인에서는 보존 기간도 정해 둔다.

## 7. 생성 단계 점검

`faithfulness`가 낮을 때:

1. 문제의 답변과 그때 들어간 컨텍스트를 **나란히 읽는다.** 대부분 여기서 원인이 보인다.
2. 컨텍스트에 근거가 있는데 딴소리면 → 프롬프트 문제. 규칙을 강화하고 인용을 강제한다.
3. 컨텍스트에 근거가 없는데 답을 지어냈으면 → abstain 정책이 안 먹고 있다. 검색 점수 임계치 게이트를 추가한다.
4. 컨텍스트에 모순된 문서가 섞여 있으면 → 검색 단계의 최신성 필터 문제. `retrieval.md`로 간다.
