## 1. 문제 정의

**무엇을 푸는가:** 고객지원 상담원(1차 응대)과 셀프서비스 사용자가 제품 사용·설정·오류에 대해 질문하면, 제품 기술문서·매뉴얼·트러블슈팅 가이드를 근거로 답하고 **출처 문서와 해당 구절을 함께 제시**한다.

**성공 기준:**
- 골든셋 40문항에서 근거 있는 정답 85% 이상
- 답이 문서에 없는 질문에서 "확인할 수 없음" 정답률 90% 이상 (지어내지 않는 것)
- 상담원이 답변의 출처를 클릭 한 번으로 원문에서 확인 가능

**범위 밖 (v1):**
- 고객 계정·주문 등 실시간 데이터 조회 (문서 검색만)
- 조치 실행 (설정 변경, 티켓 생성 등)
- 제품 문서에 없는 일반 기술 상담
- 다국어 응대 — v1은 문서 원어 + 한국어 질의까지만

## 2. 인터뷰 결과

| 항목 | 답 | 설계 영향 |
|---|---|---|
| 질문 유형 | **트러블슈팅(절차) + 사양 조회(단일 사실)** 혼재 *(도출)* | 두 유형의 최적 top-k가 다름 → v2 의도 라우팅 후보. v1은 절차 쪽에 맞춰 k=5 |
| 코퍼스 | 문서 ~1,000개, 기술문서·매뉴얼·트러블슈팅 가이드 | 소규모 → pgvector로 충분. 인프라에 시간 쓰지 않음 |
| 정답의 소재 | **대부분 단일 섹션, 버전 비교 질문만 multi-hop** *(도출)* | v1 베이스라인으로 커버 가능. multi-hop은 골든셋에서 별도 추적 |
| 접근 제어 | **없음 — 전원 동일** | acl 필드 불필요. 단 §7 위험 R4 참조 |
| 오답 비용 | **중간** | 인용 필수 + 신뢰도 낮으면 상담원 에스컬레이션. 사람 검토 단계는 불필요 |
| 예산 | **미확정** *(가정: p95 첫 토큰 3초, 월 2만 쿼리)* | 리랭커 포함 가능. §6에서 추정치 산출 |
| 신규 / 개선 | **신규** *(가정)* | 실패 사례 씨앗이 없음 → 골든셋을 지원 티켓 로그에서 만들어야 함 |

### 가정 — 틀렸을 때 다시 볼 곳

이 문서는 아래를 가정하고 쓰였다. 각 항목이 틀리면 우측 절을 다시 본다.

| # | 가정 | 틀렸다면 |
|---|---|---|
| A1 | 문서가 마크다운/HTML 등 **구조화된 형식**이고 헤딩 체계가 일관됨 | §4.1 파싱, §4.2 청킹 전면 재검토 (스캔 PDF면 OCR 품질이 상한이 된다) |
| A2 | 제품 **버전이 여러 개** 공존하고 문서도 버전별로 존재 | 맞으면 §4.3 `product_version` 필수. 단일 버전이면 해당 필터 제거 가능 |
| A3 | 문서에 **코드 예제·설정 파일·에러 코드**가 상당량 포함 | 없다면 §4.5 BM25 가중치를 베이스라인(동등)으로 되돌린다 |
| A4 | 질문과 문서의 언어가 **한/영 혼재** | 영어 단일이면 §4.4 임베딩 후보가 넓어진다 |
| A5 | 월 2만 쿼리, p95 첫 토큰 3초 | §6 비용·지연 추정 전체 |
| A6 | 지원 티켓 로그에 **실제 질문 이력이 존재** | 없으면 §3 골든셋 제작 방식을 담당자 작성 + 합성으로 변경, 일정 +1주 |

**A1과 A6은 착수 전에 반드시 확인한다.** 둘 다 설계가 아니라 일정을 바꾼다.

## 3. 골든셋

- 위치: `data/golden/product-support.jsonl`
- 목표 문항 수: **40** (dev 28 / holdout 12)
- 마지막 갱신: 미작성

### 구성

| 태그 | 비율 | 문항 수 | 이유 |
|---|---|---|---|
| `troubleshooting` | 35% | 14 | 주력 유형. 절차가 잘리면 바로 드러남 |
| `spec-lookup` | 25% | 10 | 단일 사실. 에러코드·파라미터명 정확 검색 검증 |
| `unanswerable` | 15% | 6 | **할루시네이션 측정의 필수 조건.** 없으면 faithfulness가 무의미 |
| `version-specific` | 10% | 4 | 구 버전 답변이 나오는지 — 이 도메인 최대 위험 |
| `code-config` | 10% | 4 | 코드 블록·설정 파일이 온전히 검색되는가 |
| `colloquial` | 5% | 2 | "이거 왜 안 돼요" 류 실제 말투 |

### 제작 방식

1. **지원 티켓 로그에서 실제 질문 24개 추출** (가정 A6). 가공하지 않고 원문 그대로.
2. 제품 담당자가 정답과 근거 문서를 확인 — **사람이 검증한다.** 여기서 타협하면 이후 모든 측정이 흔들린다.
3. `unanswerable` 6문항은 의도적으로 작성: 미지원 기능, 타사 제품, 아직 릴리스 안 된 기능, 문서화되지 않은 내부 동작.
4. `version-specific` 4문항은 **버전별로 답이 다른 항목**을 골라 버전을 명시한 질문과 명시하지 않은 질문을 섞는다.
5. LLM 합성은 부족분 채우기에만 사용하고 **비율을 기록한다.** 합성 질문은 문서 표현을 그대로 쓰는 경향이 있어 검색을 실제보다 쉽게 만든다 — 실전 recall을 과대평가한다.

### 항목 형식

```json
{"question": "설치 후 첫 실행에서 E-4012가 뜹니다",
 "ground_truth": "포트 8443이 이미 사용 중일 때 발생합니다. config.yaml의 server.port를 변경하거나 기존 프로세스를 종료합니다.",
 "reference_chunk_ids": ["troubleshoot-guide-v3#e-4012"],
 "product_version": "3.x",
 "tags": ["troubleshooting", "code-config"]}
```

`reference_chunk_ids`를 채우면 LLM 판정 없이 recall을 직접 계산할 수 있다 — 빠르고 싸고 결정적이다. 가능한 한 채운다.

## 4. 파이프라인

```
[인덱싱]
  문서 → 구조 기반 파싱 → 헤딩 단위 청킹(512 상한) → 컨텍스트 헤더 부착
       → 메타데이터(버전·제품·문서종류) → [BM25 인덱스 + pgvector]

[질의]
  질문 → (대화형이면) 쿼리 재작성 → 버전 필터 결정
       → BM25 top-20 ┐
                     ├→ RRF 융합 → top-20 → 리랭커 → top-5
       → 벡터 top-20 ┘
       → 검색 점수 게이트 ──(미달)──→ "확인 불가" + 상담원 연결
       → 생성(claude-opus-5, Citations) → 답변 + 출처
```

### 4.1 파싱

```
결정: 구조 보존 파서 (마크다운/HTML 헤딩 트리 유지), 코드 블록은 원문 그대로,
      표는 마크다운 표로 별도 추출, 네비게이션·푸터 제거
근거: 제품 문서는 헤딩 체계가 일관됨(A1). 이 구조가 청킹 경계와 컨텍스트 헤더의
      재료가 되므로 파싱에서 버리면 복구할 수 없다.
측정: 무작위 청크 20개 육안 검수 — 코드 블록 온전성, 표 셀 경계, 헤딩 경로
재검토: 스캔 PDF나 비정형 문서가 20% 이상이면 레이아웃 인식 파서로 전환
```

**착수 첫날 할 일:** 문서 5개를 파싱해 결과를 직접 읽는다. 자동화 전에 눈으로 본다. 여기가 나쁘면 뒷단 전체가 무의미하다.

### 4.2 청킹

```
결정: 헤딩(H2/H3) 단위 분할 + 512 토큰 상한 초과 시 문단 경계로 재분할,
      오버랩 15%, 코드 블록은 분할하지 않음
근거: 베이스라인 기본값(고정 512)에서 벗어난다. 제품 문서는 "E-4012 오류" 같은
      헤딩이 곧 의미 단위이고 이 경계를 무시하고 자르면 증상과 조치가 갈린다.
      코드 블록을 중간에서 자르면 검색돼도 쓸모가 없다.
대안: 고정 512(단순하지만 절차 분리 위험) / parent-child(문맥 유리, 구현 +1단계)
측정: context_recall, context_precision, 태그별(troubleshooting) recall
재검토: troubleshooting 태그 recall < 0.85 이면 parent-child로 전환
        — 작은 청크로 검색하고 섹션 전체를 생성에 넘기는 방식. 1순위 확장 후보다.
```

**청크 크기는 회의로 정하지 않는다.** 골든셋이 준비되면 256/512/1024 세 인덱스로 recall을 재고 30분 안에 확정한다. 차이가 작으면 작은 쪽을 택한다(비용·precision 유리).

### 4.3 메타데이터

| 필드 | 용도 | 필수 |
|---|---|---|
| `doc_id` / `chunk_id` | 인용, 중복 제거 | ✓ |
| `title` | 문서 제목 | ✓ |
| `section_path` | 컨텍스트 헤더 ("설치 > 문제 해결 > E-4012") | ✓ |
| `source_uri` | 원문 링크 — **상담원이 클릭해서 확인** | ✓ |
| `product_version` | 버전 필터 | ✓ |
| `product` | 제품군이 여럿이면 필터 | ✓ |
| `doc_type` | 매뉴얼 / API / 트러블슈팅 / 릴리스노트 | ✓ |
| `updated_at` | 최신성 정렬 | ✓ |
| `lang` | 언어 | ✓ |
| ~~`acl`~~ | 접근 제어 없음 (인터뷰 확인) | — |

**`product_version`이 이 설계에서 가장 중요한 메타데이터다.** 접근 제어가 없는 대신 버전이 그 자리를 차지한다. 나중에 추가하려면 전체 재인덱싱이므로 v1에 반드시 넣는다.

### 4.4 임베딩 / 인덱스

```
임베딩 모델: BAAI/bge-m3 (1024차원, 최대 8192 토큰)
근거: 한/영 혼재(A4) → 다국어 필수. 8192 토큰 입력이라 512 청크가 잘릴 위험 없음.
      셀프 호스팅 가능 — 제품 문서 반출 제약이 있어도 대응된다.
      (참고: Anthropic은 임베딩 API를 제공하지 않으므로 별도 조달이 필요하다)
대안: multilingual-e5-large (512 토큰 제한 — 청크 상한과 여유가 없다),
      Voyage 계열 (성능 양호, API형 — 반출 제약 확인 필요)
벡터 스토어: pgvector
근거: 문서 1,000개 × 평균 20청크 ≈ 2만 청크. 전용 벡터 DB가 필요한 규모가 아니다.
      메타데이터 필터링이 SQL로 자연스럽고 운영 부담이 낮다.
BM25: PostgreSQL 전문검색 또는 OpenSearch — 벡터와 같은 저장소에 두면 운영이 단순
측정: 골든셋 recall, 인덱싱 소요 시간
재검토: 청크 20만 초과 또는 필터링 지연이 문제가 되면 전용 엔진(Qdrant 등)
        — 임베딩 모델 교체는 전체 재인덱싱이므로 소규모 샘플 비교를 먼저 한다
```

### 4.5 검색

```
방식: 하이브리드 — BM25 top-20 + 벡터 top-20 → RRF(k=60) 융합
근거: 제품 문서는 에러 코드(E-4012), 파라미터명(server.port), 제품명 같은
      **정확한 문자열**이 질문의 핵심인 경우가 많다(A3). 벡터 단독으로는
      "E-4012"와 "E-4011"을 구분하지 못한다. RRF는 점수 정규화와 가중치 튜닝이
      필요 없어 출발점으로 적합하다.
1차 top-k: 20 (recall 확보)
리랭커: BAAI/bge-reranker-v2-m3
최종 top-k: 5 (precision 확보)
필터: product_version(질문에서 추출 또는 세션 컨텍스트), product, 사전 필터로 적용
쿼리 변환: 대화형 후속 질문 재작성만 v1 포함. 분해·다중질의는 v1 제외
근거(쿼리 재작성): "그럼 그건요?" 같은 질의는 그대로 검색하면 반드시 실패한다.
                  대화형 UI라면 선택이 아니다. 재작성 결과를 로그에 남긴다.
근거(분해 제외): multi-hop 비중이 낮다고 판단(version-specific 10%).
                측정 후 필요하면 추가한다 — 한 번에 여러 개 넣지 않는다.
측정: context_recall, context_precision, 태그별 recall, 단계별 지연
재검토: - recall < 0.85 → 아래 5단계 점검 순서를 따른다
        - spec-lookup 태그만 낮음 → BM25 가중을 RRF에서 조정
        - version-specific 태그만 낮음 → 버전 필터 추출 로직 문제
```

**recall이 낮을 때 점검 순서** (순서대로, 건너뛰지 않는다):
1. 정답 청크가 인덱스에 있는가 → 없으면 파싱·청킹 문제 (§4.1/4.2)
2. chunk_id로 직접 조회한 내용이 온전한가 → 잘렸으면 청킹 문제
3. 질문 용어와 청크 용어가 다른가 → 약어·동의어 문제
4. BM25 단독으로는 찾히는가 → 찾히면 RRF 가중 조정
5. top-k를 50으로 늘리면 들어오는가 → 들어오면 랭킹, 아니면 임베딩·인덱스 문제

### 4.6 생성

```
모델: claude-opus-5
근거: 오답 비용 중간 + 트러블슈팅은 조건 판단이 들어간다. 비용 인하는 골든셋으로
      손실을 수치화한 뒤 결정할 사안이지 설계자가 임의로 내릴 일이 아니다.
      (§6에 claude-sonnet-5 비교 추정 포함 — 판단 근거로만 제시)
thinking: {"type": "adaptive"}  — budget_tokens는 현행 모델에서 400을 반환한다
effort: "medium" (spec-lookup 경로는 "low" 검토)
max_tokens: 16000 (비스트리밍) / 스트리밍 사용 시 상향
스트리밍: 사용 — 상담원 대면이므로 첫 토큰 지연이 체감 품질을 좌우한다
인용: Citations API (각 document 블록에 citations.enabled = true)
근거(인용): 프롬프트로 [1] 마커를 요구하면 모델이 번호를 틀리는 일이 흔하다.
           API가 인용 범위를 직접 표시하므로 번호가 틀어지지 않고, cited_text와
           위치 정보를 그대로 UI 출처 링크로 쓸 수 있다.
제약: Citations는 구조화 출력(output_config.format)과 병용 불가(400).
      답변을 JSON 스키마로 강제해야 한다면 인용을 포기해야 하므로,
      이 설계는 **인용을 택했다.**
abstain: 리랭커 최고 점수 < 임계치 → 생성을 건너뛰고 고정 문구 + 상담원 연결
근거(abstain): LLM에게 맡기는 것보다 점수 게이트가 확실하다. 오답 비용 중간이므로
              "틀린 답"보다 "연결"이 낫다.
측정: faithfulness, answer_relevancy, unanswerable 태그 정답률, abstain 비율
재검토: faithfulness < 0.90 → 프롬프트 규칙 강화 → 그래도 낮으면 점수 임계치 상향
```

**시스템 프롬프트 골자:**

```
당신은 <제품> 기술문서를 근거로 답하는 고객지원 어시스턴트입니다.

- 제공된 문서에 있는 내용만으로 답합니다. 일반 기술 지식으로 보충하지 않습니다.
- 모든 사실 주장에 근거 문서를 표시합니다.
- 문서에 답이 없으면 "제공된 문서에서 확인할 수 없습니다"라고 답하고,
  무엇을 찾아봤는지 알려준 뒤 상담원 연결을 안내합니다.
- 문서들이 서로 다른 제품 버전을 가리키면 버전을 명시해 구분해 답하고,
  질문에 버전이 없으면 어느 버전 기준인지 되묻습니다.
- 추측을 답처럼 쓰지 않습니다.
```

네 번째 규칙이 이 도메인의 핵심이다. 릴리스노트와 구 버전 매뉴얼이 함께 검색되는 일이 잦고, 모순을 지적하지 않는 시스템은 조용히 틀린 답을 낸다.

**프롬프트 캐싱:** 시스템 프롬프트와 고정 용어집은 캐시 대상, 검색된 청크는 매 쿼리 달라지므로 **마지막 캐시 breakpoint 뒤**에 둔다. 다만 시스템 프롬프트가 짧으면(모델별 최소 512~4096 토큰) 캐시가 조용히 안 걸린다 — `usage.cache_read_input_tokens`로 반드시 확인한다. 0이 계속 나오면 캐싱을 비용 계산에서 뺀다.

## 7. 위험과 대응

| # | 위험 | 영향 | 대응 | 확인 방법 |
|---|---|---|---|---|
| **R1** | **버전 혼입** — 구 버전 문서와 신 버전 문서가 함께 검색돼 구 버전 조치를 안내 | 고객이 잘못된 조치를 실행. 이 도메인 최대 위험 | `product_version` 사전 필터 + 프롬프트의 버전 구분 규칙 + 개정 시 구 청크 삭제 | `version-specific` 태그 recall과 오답 내용 |
| **R2** | **코드 블록 분할** — 설정 예제가 중간에서 잘려 검색돼도 쓸모없음 | 트러블슈팅 답변 품질 저하 | 청킹 시 코드 블록 분할 금지 | `code-config` 태그 recall + 청크 육안 검수 |
| **R3** | **에러 코드 검색 실패** — 벡터 검색이 유사 코드를 구분 못 함 | spec-lookup 실패 | 하이브리드 + BM25 가중 | `spec-lookup` 태그 recall, E-40xx 계열 교차 검증 |
| **R4** | **내부용 문서 유출** — 접근 제어가 "없다"고 했으나 내부 전용 문서가 코퍼스에 섞여 셀프서비스 사용자에게 노출 | 정보 유출 | 인덱싱 대상 목록을 **명시적 화이트리스트**로 관리. 전체 크롤 금지 | 인덱싱 로그의 문서 목록 검토 |
| **R5** | **문서 개정 후 구 청크 잔존** | 모순된 답변 | 문서 단위 upsert 시 기존 청크 선삭제 | 인덱싱 로그의 삭제 건수 |
| **R6** | **골든셋을 합성으로 채움** | 실전 recall 과대평가 | 실제 티켓 질문 60% 이상 유지, 합성 비율 기록 | 골든셋 메타데이터 |
| **R7** | **프롬프트 주입** — 문서에 지시문이 포함 (특히 외부 기여 문서) | 의도하지 않은 동작 | 문서는 데이터이지 지시가 아님을 시스템 프롬프트에 명시, 문서 블록 경계 명확화 | 주입 시나리오 테스트 문항 추가 |

R1과 R4가 이 설계에서 가장 비싼 실패다. 둘 다 **v1 착수 시점에** 대응이 들어가야 하고, 나중에 붙이면 재인덱싱이다.

## 8. 운영

**인덱스 갱신**
- 문서 해시 비교로 **변경분만** 재처리
- 문서 수정 시 기존 청크 **선삭제 후** 삽입 (R5)
- 문서 삭제 시 인덱스에서도 삭제
- 전체 재인덱싱이 필요한 변경: 임베딩 모델 교체, 청킹 전략 변경, 메타데이터 스키마 변경 → 블루/그린으로 새 인덱스를 만들고 골든셋 통과 후 전환

**로깅 (쿼리별)**
```
timestamp, session_id, 원 질문, 재작성된 질의, 적용된 버전 필터,
검색된 chunk_id + 점수(BM25/벡터/RRF/리랭크), 최종 top-5,
답변, 인용 목록, abstain 여부, 단계별 지연, 토큰 사용량
```
재작성된 질의와 버전 필터를 안 남기면 실패 원인 추적이 불가능하다.

**모니터링**

| 지표 | 경보 조건 |
|---|---|
| abstain 비율 | 기준선 대비 급등 → 인덱스·검색 이상 |
| 인용 0개 답변 비율 | 0에 가까워야 함 |
| 평균 리랭크 최고 점수 | 하락 추세 → 질문 분포가 코퍼스에서 벗어나는 중 |
| p95 지연 (단계별) | 목표 초과 |
| 상담원 에스컬레이션율 | 급등 시 원인 조사 |
| 👎 피드백 | 큐에 적재 → 정기 검토 → **재현되면 골든셋에 추가** |

골든셋은 정적인 문서가 아니라 자라는 자산이다.

**캐싱**
- 응답 캐시: FAQ성 반복 질문에 효과적. 인덱스 갱신 시 무효화. (접근 제어가 없어 권한별 분리는 불필요)
- 프롬프트 캐시: §4.6 참조 — 실효성을 `cache_read_input_tokens`로 확인한 뒤 비용 계산에 반영

**롤아웃**
1. 내부 상담원 소수에게 먼저 — 실패 사례를 빠르게 모으는 것이 목적
2. **abstain 임계치를 넉넉하게 시작**한다. 초기에 틀린 답이 많은 것보다 "확인 불가"가 많은 편이 신뢰 확보에 낫다. 데이터가 쌓이면 조인다
3. 인용 UI는 **1일차부터**. 나중에 붙이는 기능이 아니다
4. 셀프서비스 공개는 내부 운영 지표가 목표를 만족한 뒤

| 5 | CI 회귀 게이트 연결 | 자동 실행 | 2일 |
| 6 | 내부 상담원 제한 롤아웃 | 실패 사례 30건 수집 | 2주 |

**v2 후보** (베이스라인 측정 후 필요성이 확인되면):
- parent-child 청킹 (troubleshooting recall이 낮을 때 — 1순위)
- 의도 라우팅 (유형별 품질 편차가 클 때 — 품질·비용 동시 개선)
- 쿼리 분해 (version-specific·비교 질문이 실패할 때)
- 용어 사전 (제품 약어로 인한 검색 실패가 확인될 때)

순서대로 간다. 한 번에 여러 개 넣으면 무엇이 기여했는지 알 수 없다.
